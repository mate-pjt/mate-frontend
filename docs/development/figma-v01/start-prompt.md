# 새 대화에서 Task 하나를 시작하는 프롬프트

같은 `/Users/jisung/mate-frontend` 프로젝트의 새 대화에서 아래 문구를 사용한다. `작업 ID`만 WBS에서 선택한 하나로 바꾼다. `PREP-01`은 다음 작업의 예시다. 실제 API 변경·서비스 운영·배포는 이 프롬프트의 Git 전달 승인에 포함하지 않는다.

```text
저장소: /Users/jisung/mate-frontend
작업 ID: PREP-01 하나만

먼저 /Users/jisung/mate-frontend/AGENTS.md와
/Users/jisung/mate-frontend/docs/development/figma-v01/README.md를 읽고,
연결된 workflow·해당 작업 기록·필요한 선행 결정/QA 기록을 확인해줘.
전체 과거 대화나 모든 작업 기록을 읽는 대신 이번 작업에 필요한 근거를 골라 읽어줘.

$feature-workflow를 적용하고, 현재 branch/HEAD·미커밋 변경·선행 작업의
main 반영 여부를 확인해줘. 새 독립 작업이면 최신 main에서 작업 브랜치를 만들고,
선행 변경이 아직 main에 없으면 임의 전환하지 말고 의존 관계와 진행안을 제시해줘.
기존 변경을 삭제/reset/stash하거나 관련 없는 변경을 섞지 마.

읽은 규칙, 요구사항·범위·성공 기준, 수정 파일·영향·단계·검증 계획을
편집 전에 먼저 제시하고 해당 Task 범위만 수행해줘.
정책·API·예외를 임의 확정하거나 새 라이브러리를 임의 추가하지 마.
이미 승인된 범위는 반복 승인받지 말고, 실제 API mutation은 승인된
테스트 계정과 변경/복구 범위를 확인해줘. .env·비밀값·개인정보는 읽거나 출력하지 마.

계획한 검증·Documentation Update Check·verifier·$ai-review를 수행하고,
수정 후에는 필요한 재검증/재검토를 해줘. mock 결과를 실제 API PASS로 바꾸지 마.
작업 기록에 결정·체크포인트·검증/리뷰 근거·다음 첫 행동을 남기고 WBS를 갱신해줘.

이번 Task의 Git 전달은 목적별 작은 커밋, 작업 브랜치 push, PR 작성·라벨,
CI 확인, main 병합, 로컬 main의 fast-forward 동기화까지 진행해줘.
커밋 메시지는 영어 타입과 한국어 설명으로 작성하고 런타임·테스트·문서는
가능한 별도 커밋으로 나눠줘. PR은 .github/pull_request_template.md를 따라줘.
미해결 검증/리뷰/CI 실패나 정책 차단을 숨기고 병합하거나 보호 규칙을 우회하지 마.
push·병합은 배포 완료를 뜻하지 않으며 배포 작업은 별도 범위야.

마지막에 작업 판정과 Git 전달 상태를 구분해 보고하고,
main 동기화·작업트리 상태·PR·커밋·검증·남은 차단·다음 Task를 알려줘.
다음 Task는 자동으로 시작하지 마.
```

이 문구의 Git 전달 범위는 새 대화에서 사용자가 그대로 요청했을 때 적용한다. 문서가 존재하는 것만으로 모든 후속 작업의 외부 쓰기를 자동 승인한 것은 아니다. 필요한 승인 근거가 이미 있으면 같은 승인을 반복해서 묻지 않는다.

한 Task가 여러 날 이어지면 같은 대화에서 계속한다. 컨텍스트가 커져 대화를 바꿀 때는 마지막 체크포인트를 먼저 남긴다. 같은 폴더에서는 한 작업만 파일을 수정한다. 병렬 개발이 필요하면 커밋된 기준선에서 작업별 worktree를 별도로 구성한다.
