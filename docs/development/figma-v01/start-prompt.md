# 새 대화에서 Task 하나를 시작하는 프롬프트

같은 `/Users/jisung/mate-frontend` 프로젝트의 새 대화에서 아래 문구를 사용한다. `Task ID`만 WBS에서 선택한 하나로 바꾼다. `PREP-01`은 다음 작업의 예시다. 실제 API 변경·서비스 운영·배포는 이 프롬프트의 Git 전달 승인에 포함하지 않는다.

```text
저장소: /Users/jisung/mate-frontend
Task ID: PREP-01

이번 대화에서는 위 Task 하나만 수행해줘.

1. 규칙과 작업 맥락 확인
- /Users/jisung/mate-frontend/AGENTS.md와
  /Users/jisung/mate-frontend/docs/development/figma-v01/README.md를 먼저 읽어줘.
- 연결된 workflow·기준선·해당 Task 기록·필요한 선행 결정과 QA 기록을 확인해줘.
- 전체 과거 대화나 모든 Task 기록을 읽기보다 이번 작업에 필요한 근거를 골라 읽어줘.
- $feature-workflow를 적용하고, 문서 정합성이 의심되면 $context-audit을 수행해줘.

2. Git 상태와 시작 기준 확인
- 현재 branch/HEAD·미커밋 변경·선행 작업의 main 반영 여부를 확인해줘.
- 작업트리가 깨끗하고 선행 조건이 충족되면 원격 main을 확인·동기화한 뒤
  Task에 맞는 작업 브랜치를 만들어 진행해줘.
- 선행 변경이 main에 없거나 다른 미커밋 변경이 있으면 이를 보존하고 진행안을 제시해줘.
- 기존 변경을 임의로 삭제/reset/stash하거나 이번 Task의 커밋에 섞지 마.

3. 요구사항과 실행 계획 제시
- 적용할 규칙, Task 유형, 현재 상태, 범위·제외 범위·성공 기준을 정리해줘.
- 수정 대상 파일·영향·실행 단계·검증 방법을 편집 전에 먼저 제시해줘.
- 명확한 사항은 승인된 범위에서 계속 진행해줘.
- blocking ambiguity가 있으면 최대 3개 질문과 추천안으로 확인해줘.
- 정책·API·예외를 임의로 확정하거나 새 라이브러리를 임의로 추가하지 마.

4. 해당 Task 수행
- 작업 기록의 범위만 수행하고, 코드 변경이 없는 Task에 임의로 구현을 추가하지 마.
- 기존 구조·TypeScript/React 스타일·Tailwind 토큰 규칙을 유지해줘.
- API·mock·DTO·데이터 흐름을 다루기 전에는 data-access.md를 확인해줘.
- 이미 승인된 범위는 반복 승인받지 마.
- 실제 API mutation·서비스 운영·배포는 해당 작업에 적용되는 승인 범위를 확인해줘.
  아래 Git 전달 승인이 이 행위들을 자동으로 포함하는 것은 아니야.
- .env 실제 값·비밀값·개인정보는 요청하거나 읽거나 출력하지 마.
- 중요한 결정·수행 결과·미완료 사항·다음 첫 행동을 작업 기록에 수시로 남겨줘.

5. 검증과 Review Gate
- 현재 package.json과 실행 환경을 확인하고 Task에 맞는 검증을 수행해줘.
- 구현·mock/HTTP 대역·실제 API 통합 결과를 구분하고 미실행을 PASS로 처리하지 마.
- 검증 실패 시 실제 원인에 따라 최소 수정하고 재검증해줘.
  자동 수정은 최대 3회이며, 계속 실패하면 원인·시도·차단 조건을 보고해줘.
- Documentation Update Check를 수행하고 작업 기록·QA·WBS를 갱신해줘.
- read-only verifier와 $ai-review를 수행해줘.
- 검토 후 코드나 문서가 바뀌면 필요한 재검증·재검토를 수행해줘.
- 미해결 검증·리뷰·정책 차단을 숨기고 완료 처리하지 마.

6. 커밋부터 main 동기화까지
- 검증·리뷰를 통과한 변경은 목적별 작은 커밋으로 나눠줘.
- 커밋 메시지는 영어 타입과 한국어 설명으로 작성해줘.
- 도메인이 다르면 나누고, 런타임·테스트·문서·설정도 가능한 별도 커밋으로 분리해줘.
- 작업 브랜치를 push하고 PR을 작성해줘.
- /Users/jisung/mate-frontend/.github/pull_request_template.md를 참고하고 적절한 라벨을 달아줘.
- 실제 PR head의 원격 CI와 병합 조건을 확인해줘.
- 조건이 충족되면 작은 커밋 이력을 유지하는 방식으로 main에 병합하고,
  로컬 main을 fast-forward로 동기화해줘.
- force push·보호 규칙 우회·임의의 직접 main push로 해결하지 마.
- 이 Git 전달 범위는 이번 요청으로 승인한 것이므로 같은 승인을 다시 묻지 마.

7. 완료 또는 차단 보고
- Task 판정과 Git 전달 상태를 구분해서 보고해줘.
- 변경 파일, 검증·리뷰 결과, 커밋·PR·CI, 로컬/원격 main SHA 일치와
  작업트리 상태, 미실행·차단·남은 사항을 알려줘.
- WBS의 우선순위·선행 조건·차단 상태를 확인해 다음 Task 하나를 선정하고,
  그 ID·선정 이유·다음 첫 행동을 WBS와 작업 기록에 남겨줘.
- 다음 대화에서 사용할 Task ID를 마지막에 명확히 알려줘.
- 다음 Task는 이 대화에서 자동으로 시작하지 마.
```

이 문구의 Git 전달 범위는 새 대화에서 사용자가 그대로 요청했을 때 적용한다. 문서가 존재하는 것만으로 모든 후속 작업의 외부 쓰기를 자동 승인한 것은 아니다. 필요한 승인 근거가 이미 있으면 같은 승인을 반복해서 묻지 않는다.

한 Task가 여러 날 이어지면 같은 대화에서 계속한다. 컨텍스트가 커져 대화를 바꿀 때는 마지막 체크포인트를 먼저 남긴다. 같은 폴더에서는 한 작업만 파일을 수정한다. 병렬 개발이 필요하면 커밋된 기준선에서 작업별 worktree를 별도로 구성한다.
