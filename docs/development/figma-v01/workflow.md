# 작업을 며칠에 걸쳐 이어가는 방법

기존 [feature-workflow](../../../.codex/skills/feature-workflow/SKILL.md)의 요구사항 → 설계 → 구현 → 검증 → 문서 갱신 → Review Gate → PASS 순서를 유지한다. 이 문서는 그 흐름에서 어디에 상태/맥락/증거를 남기는지 정한다.

## 문서의 책임

| 문서 | 역할 | 갱신 시점 |
| --- | --- | --- |
| baseline.md / baseline/*.json | 당시 디자인·구현·검증의 고정 출발점 | 덮어쓰지 않음. 새 기준선은 별도 버전 |
| README.md(WBS) | 현재/다음 작업·유형·우선순위·의존성·상태의 단일 기준 | 착수/단계 변경/차단/완료 시 |
| coverage.md | 79개 원본 항목과 실행 작업의 역추적 | 작업 추가/분할/제외 시 |
| tasks/작업ID.md | 요구사항·설계·결정·체크포인트·검증/리뷰·재개 위치 | 작업 중 수시, 중단/인계 전 필수 |
| docs/qa/기능.md | 실제 UI/API 사례의 통과·실패·대기·차단 및 증거 | 실제 검증할 때 기존 case ID 유지 |
| docs/ai-context/plan.md·harness.md | 프로젝트 공통 진입점과 작업 규칙 | 하네스/전체 계획 변화 시 |

WBS 상태를 작업 파일/HTML/다른 보드에 중복해 최신값처럼 관리하지 않는다. 체크리스트·로그에는 해당 시점 결과와 날짜를 기록한다. 보고서 HTML은 기준선 참고 자료다. 이 WBS는 로컬 실행 기록이며 원격 이슈 도구와 자동 동기화하지 않는다.

## 시작·재개

1. `git status --short --branch`, `git rev-parse HEAD`로 현재 작업트리와 기존 변경을 확인한다. 정리/reset/stash를 임의 실행하지 않는다. 변경된 파일 전체를 지금 작업의 결과로 간주하지 않는다.
2. 기준선 → WBS의 현재/다음 작업 → 해당 작업의 마지막 체크포인트 → 선행 작업의 결정/증거 순서로 읽는다. 기존 `AGENTS.md`, `base.md`, `architecture.md`, 필요한 `data-access.md`도 읽는다.
3. 이전 실행과 branch/HEAD/소스/디자인/API/배포가 달라졌으면 관련 사실과 무효화된 증거를 기록한다. 당시 snapshot 판정을 현재 동작으로 재사용하지 않는다.
4. 새 작업의 요구사항 Gate에서 성공 기준·범위·현재 패턴·수정 후보·검증 방법·승인 근거를 확정한다. 기존 기록은 후보 정의이며 구현 설계를 대신하지 않는다. blocking ambiguity는 최대 3개 질문과 추천안으로 해소한다.
5. 파일·영향·구현 단계·검증 계획을 편집 전에 제시한다. WBS에서 한 작업만 `진행`으로 바꾸고 branch/HEAD·기존 변경·시각·첫 행동을 작업 기록에 남긴다.

이번 문서화 승인으로 앱 개발, 실제 QA, 외부 데이터 변경이 시작되는 것은 아니다. `준비`는 다음 요구사항 Gate 대상으로 선택됐다는 뜻이다. 이미 승인된 행위는 반복 승인받지 않으며, 없는 승인·계약을 시간 경과나 문서 생성으로 대신하지 않는다.

## 상태와 완료 기준

| 상태 | 의미와 전환 조건 |
| --- | --- |
| 대기 | 순서·선행 결과 또는 아직 확정하지 않은 착수 범위 대기. 선행 완료만으로 자동 시작하지 않음 |
| 준비 | 다음 작업으로 선택됨. 요구사항 Gate/현행 조건 확인 후 진행 |
| 진행 | 요구사항·설계 후 해당 단위 실행 중. 중간 결정/수정/미완료를 수시 기록 |
| 검증 | 구현/준비 산출물이 있어 계획한 검증 수행 중. 실패는 원인·수정·재검증 기록 |
| 리뷰 | 필수 검증 결과와 Documentation Update Check 후 verifier/ai-review 수행 중 |
| 차단 | 환경·계정·데이터·계약 같은 구체적 외부 조건으로 진행 불가. 원인/필요 담당 역할/재개 조건/마지막 확인일 필수 |
| 보류 | 조건부 기능·미지원/범위 제외·회귀 트리거 대기. 결정 근거와 재검토 조건 기록. 완료로 집계하지 않음 |
| 완료 | 정의된 단위의 필수 검증·문서·Review Gate 근거 확보. 구현 코드 존재만으로 완료하지 않음 |

한 번에 `진행/검증/리뷰`는 하나다. 대기/차단/보류는 실패를 숨기는 완료 상태가 아니다. 작업을 분할하면 원래 ID와 새 ID, 남은 범위·의존성·원본 연결을 함께 남긴다.

개발 작업 자체에 해당 기능의 검증이 포함된다. 정책 작업의 완료는 결정된 범위를 의미하며 제품 구현 완료가 아니다. 기존 구현의 QA 작업은 실제 통합 증거를 보완한다. mock/HTTP 대역/정적 화면/실서버 통합 결과는 각각 표시하고 상호 대체하지 않는다.

## 검증·실패·문서 갱신

- 런타임 변경은 현재 `package.json`을 확인해 `pnpm test`, `pnpm lint`, `pnpm build`, `git diff --check`를 기본으로 실행한다. Storybook/공유 UI 영향 시 `pnpm build-storybook`도 수행한다. 데이터 변경 시 API/mock/hybrid·guard·계정 격리 등 기존 Gate를 적용한다. async Server Component는 실제 Next/브라우저에서 확인한다.
- Markdown/기준선 JSON만 바꾸고 실행 코드·패키지·빌드 설정에 영향이 없는 문서 작업은 문서 링크·ID/79개 커버리지·의존성/상태·스냅샷 무결성·범위 보존 검사와 `git diff --check`를 검증 계획에 넣을 수 있다. 영향 없는 앱 test/lint/build는 미실행 사유를 기록한다. 이 선택은 앱 기능 변경 검증의 면제 규칙이 아니다.
- 실제 API QA는 기존 `docs/qa/README.md` 양식에 실행 식별자·브라우저/크기·시각·단계·UI/비식별 Network 증거·복구를 남긴다. `.env` 값, token/cookie, 인증번호, 초대/서명 URL, 원본 문서·개인정보는 남기지 않는다.
- 실패 시 실제 오류 → 최소 수정 → 실패 검사 재실행 → 영향 검사 재실행. 자동 수정은 최대 3회다. 세 번째 실패 뒤 원인/시도/막힌 조건과 필요한 결정을 보고한다.
- package/scripts는 base, 구조/API/mock/component는 architecture/data-access, 계획/상태는 WBS/plan, 반복 실패/하네스 변화는 ai-failures/harness 갱신을 검토한다. 변경이 없으면 문서별 미갱신 이유를 적는다.
- 다중 파일/하네스/외부 디자인 해석 작업은 read-only verifier와 ai-review를 실행한다. ai-review 여섯 섹션과 대상 diff/증거를 보존한다. 검토 뒤 변경 시 해당 검토를 다시 실행하거나 최종 보고에 재실행하지 않은 구체적 이유를 쓴다.

## 차단과 승인 예외

1. 작업 기록에 막힌 단계·원인·필요 담당 역할/결정·재개 조건·현재 복구 상태를 쓴다. WBS를 차단으로 바꾸되 원본 기준선과 기존 QA의 통과/대기 이력을 보존한다.
2. 기존 승인된 예외가 있으면 원문/날짜·적용 작업·남은 사례를 연결한다. Mailpit 때문에 미뤄진 수신처 인증 예외를 다른 API QA나 새 기능에 확대하지 않는다.
3. 필수 검증 PASS 전에는 다음 기능으로 자동 이동하지 않는다. 해당 단위에 적용되는 기존 예외가 없으면 구체적인 미실행 범위와 추천안을 제시해 개발자 결정을 받는다. 독립된 문서 정리·승인된 준비 작업은 그 범위 안에서 진행할 수 있다.
4. 예외로 진행이 허용돼도 실제 QA는 차단/대기 상태로 남긴다. 실행 범위가 제한된 완료와 기능 전체 통합 PASS를 구분한다. 예외 범위·승인자·사유·후속 작업을 기록하지 않은 채 완료로 바꾸지 않는다.
5. 재개 시 환경·소스/배포·승인·fixture를 다시 확인한다. 현재 API 준비 여부를 백엔드 옛 브랜치나 `GENERAL` 같은 유사 값으로 추정하지 않는다.

## 중단·완료 시 기록

중요 단계가 끝날 때, 오래 기다리기 전, 대화를 끝내기 전에 작업 파일에 아래를 남긴다. 끝에 한꺼번에 복원하려 하지 않는다.

```text
시각 / 실행자 / branch·HEAD·dirty 범위
이번에 완료한 것 + 근거 경로·case·명령 결과
현재 수정/미완료·실패 및 자동 수정 횟수
확정 결정·가정·승인 예외와 출처
차단 원인·필요 담당 역할·재개 조건
다음 첫 행동(읽을 파일 또는 실행할 구체적 단계)
검증/Review Gate 대상·결과·후속 변경 재검토 여부
커밋/PR 또는 미커밋 사실, 데이터/프로세스 복구 상태
```

완료 후 작업 체크리스트/증거·기존 QA를 갱신하고 WBS를 완료로 바꾼다. 현재 작업을 비우고 다음 작업 **하나**와 첫 행동을 지정한다. 다음 기능은 새 요구사항 Gate부터 시작한다. 커밋/PR을 만들 경우 목적별 작은 단위와 프로젝트 Conventional Commits/PR 템플릿 규칙을 따른다. 문서화가 커밋/푸시/배포를 자동 실행하는 것은 아니다.

## 새 대화의 Git 전달 범위

[고정 시작 프롬프트](start-prompt.md)에서 커밋/push·PR·CI·main 병합/로컬 동기화까지 명시적으로 요청한 경우 [전체 Task 흐름](task-cycle.md)을 수행한다. 같은 승인을 다시 묻지 않으며, 미해결 검증/정책/CI 차단과 병합 보호 규칙은 준수한다. 마지막 보고는 작업 검증 판정과 Git 전달 상태를 구분한다. push나 main 병합이 배포 완료를 뜻하지 않는다.
